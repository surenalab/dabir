Project plan · v0.1 · September 2026

Dabir

An open source, local-first workspace where a paper, its code, its Git history, and its AI agents live in one window. Overleaf-quality editing with the control of your own machine.

NameDabir (دبیر), the Persian word for scribe, from Middle Persian dibīr: the person who wrote, kept and copied the texts. Alternatives considered: Resaleh (رساله, treatise) and Daftar (دفتر, notebook).
LicenceAGPL-3.0 for the app, MIT for the editor packages.
OwnerSadegh Salehi

1. The thesis

Overleaf is where coauthors are, but it is paid for anything beyond the basics, keeps your files on its servers, and cannot run your experiments. VS Code plus LaTeX Workshop plus Claude Code can do everything, but writing a paper in it feels like editing config files. LMMs-Lab Writer sits between the two and already has a local AI panel and Git, but no collaboration story and a generic UI.

Dabir's bet is narrow on purpose: the paper is a Git repo that also contains the experiment code, and the agent is a coauthor that can rerun figures and edit the manuscript in the same change. Collaboration rides on GitHub first and real-time editing second. The visual editor is the thing people will screenshot, so it has to be the best-looking LaTeX surface that exists.

One-line pitch. "T3 Code for scientists": a beautiful native app that opens your paper repo, shows LaTeX like a document, compiles locally, and lets the agent you already pay for, whether Claude, Codex, Grok or Cursor, regenerate the figure, update the table, and open the pull request.

2. Principles

  • Git is the truth. No proprietary project format. A Dabir project is a folder with a main.tex and optionally a dabir.toml. Delete the app and nothing is lost.
  • Local by default, cloud by choice. Compile, Git, search and agents work offline. Sync, sharing and live cursors are opt-in services you can self-host.
  • Agents are coauthors, not chatbots. They get the whole repo, a terminal, the compile log, and produce diffs you review, never silent edits.
  • Meet coauthors where they are. Import and export Overleaf projects; push and pull through the Overleaf Git bridge for people who have it.
  • Design is the product. If a screen would not pass an Apple design review, it is not done.

3. What it looks like

Three-pane macOS layout: navigator, document, inspector. The visual editor renders math, figures and citations inline while the underlying file stays plain LaTeX.

The UI follows Apple's Human Interface Guidelines for a document-based Mac app: a translucent sidebar, a unified toolbar, an inspector on the right, sheets for share and settings, native menus and shortcuts. It should feel like Pages or Xcode, not like a web app in a frame. On Windows and Linux the same structure holds with platform-appropriate chrome.

Core screens

  1. Open or clone. Recent projects, "Clone from GitHub", "Import from Overleaf (.zip or Git link)". The first thing a new user sees, so it has to sell the product in one glance.
  2. Document. Visual mode by default, source mode one keystroke away, split PDF preview with SyncTeX click-through.
  3. Agent inspector. Prompt, live tool log, diff, accept or reject per hunk, commit or open PR. Provider picker in the header: Claude Code and Codex on day one, Cursor, Grok and OpenCode after.
  4. Changes. Git history as a document timeline. Each commit shows the rendered pages that changed, not just lines.
  5. Share sheet. Invite via GitHub collaborators, or start a live session with a link.

5. Agents: any subscription, shared memory

Bring the agent you already pay for

Dabir never proxies model calls through its own servers. Each vendor's own agent runs as a local sidecar process, signed in with the user's existing subscription, and Dabir talks to it over one internal event protocol: prompt in, tool calls and file edits out, diff at the end. The user picks a provider per project, or per task, from a menu in the inspector.

ProviderHow it runsWhat you sign in with
ClaudeClaude Code CLI via the Agent SDKClaude Pro or Max, or an Anthropic API key
OpenAICodex CLIChatGPT Plus or Pro, or an OpenAI API key
CursorCursor agent CLICursor subscription
GrokGrok Build CLISuperGrok subscription or xAI key
Anything elseOpenCode, or any Agent Client Protocol serverWhatever that tool accepts, including local models via Ollama

The adapter layer targets the Agent Client Protocol (ACP) first, since Claude Code, Codex and Gemini already speak it through adapters, and adds thin native adapters where a vendor exposes richer events. New providers are a single file. The mock in section 3 shows the provider name in the inspector header for this reason.

Terms of service risk. Whether a subscription may be driven from a third-party app is decided by each vendor and has changed before. Dabir only ever launches the vendor's own official CLI, exactly as the user could from a terminal, and always keeps the API-key path working so no provider can strand a project.

Memory that lives in the repo

The problem with agent memory in a paper project is that three coauthors use three different agents, and none of them remember what the others learned. Dabir solves this by making memory a set of plain files, committed to Git, that every agent reads and maintains.

LayerWhereHolds
Project brief.dabir/PROJECT.md, committedWhat the paper claims, target venue and page limit, notation conventions, macro list, which script produces which figure and table, how to run the experiments. Auto-drafted on first open, then maintained by agents and reviewed like any other diff.
Facts.dabir/memory/*.md, committedOne fact per file with frontmatter: a reviewer's comment and how it was addressed, a decision about a baseline, a dataset quirk. Agents write these after an accepted run; humans can edit them in the app like notes.
Provenance.dabir/provenance.json, committedA graph from every figure, table and number in the text back to the command, script, data hash and commit that produced it. This is what makes "rerun what feeds Figure 3" and "which results are stale after this code change" possible.
Index.dabir/index/, gitignoredLocal embedding and symbol index over .tex, code, .bib and compile logs, updated incrementally on save. Gives agents retrieval over a 40-page paper plus a codebase without stuffing it all into context.
Personal~/.dabir/<project>/, never committedYour own writing preferences, provider choice, and session transcripts. Keys live in the OS keychain.

Every vendor CLI looks for its own instructions file, so Dabir generates AGENTS.md, CLAUDE.md and .cursor/rules as one-line pointers into .dabir/PROJECT.md. One source of truth, no drift between agents. Each agent run starts on a Git worktree, gets the brief, the relevant facts by retrieval, and the provenance subgraph for whatever it was asked to touch. When the user accepts the diff, the agent's proposed memory updates are shown as part of the same review and committed together with the change, so memory is never ahead of or behind the code.

The provenance graph is also what lets agents manage the repo rather than just edit it: mark a result stale when its script changes, refuse to edit a number in the text that is generated from a table, propose a commit message that names the figure and the experiment, and keep the manuscript and the code in one reviewed change.

6. Design workflow

Two agent skills drive every UI change, and they are installed in the repo so every contributor's agent uses them.

  • Impeccable for direction and craft: run /impeccable init once to produce DESIGN.md from the brief below, then /audit, /critique and /polish on every screen before merge. Its typography procedure rejects default faces, which suits us.
  • Apple design skill for platform correctness: sidebar and inspector behaviour, toolbar density, sheet versus popover, keyboard and accessibility expectations, dark mode and vibrancy. Used as a reviewer on every PR that touches UI.
# in the repo root
npx impeccable install
npx skills add https://github.com/NutshellEngineering/apple-design-skill
# then inside Claude Code
/impeccable init

Design brief (input to Impeccable init)

  • Subject. A manuscript editor for researchers. The world is paper, ink, proof marks, journal typography.
  • Feel. Quiet, dense, precise. Think Pages meets Xcode with the calm of a printed page. No gradients, no glass for its own sake.
  • Type. System UI face for chrome (SF Pro on Mac). Document view uses a serif that resembles the compiled paper: STIX Two or Latin Modern. Mono for source and logs: a face with a real italic.
  • Colour. Warm paper ground, graphite text, one accent: proofreader's red (madder, near #A8322D) for actions, diffs and the compile button. Semantic green and amber only for status.
  • Density. Editor is generous; navigator and inspector are compact. Reading text stays near 65 characters.
  • Motion. Only where it explains state: a diff hunk sliding in, a compile progress ring, a cursor arriving. Respect reduced motion.

8. Risks and how we hold them

  • Visual LaTeX is a tar pit. Ship source plus preview first. Visual mode covers headings, paragraphs, math, figures, citations, lists and tables, and drops to source for anything else. Never pretend.
  • Overleaf adds agents. They will. Our moat is local control, running code, and Git-native review. Keep those three ahead.
  • Real-time editing on top of Git. Hard. Delay it to phase 3 and design the data model for it from phase 0 so it does not need a rewrite.
  • TeX distribution across OSes. Tectonic solves most of it. Keep "use system TeX Live" for the long tail.
  • Vendors close their CLIs to third parties. Keep the API-key path first-class and the adapter layer thin, so losing one provider costs a menu entry, not the product.
  • Solo maintainer burnout. Phases 1 and 2 are cuttable to a compelling alpha on their own. Recruit two contributors before phase 3.
